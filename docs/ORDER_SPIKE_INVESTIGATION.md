# 订单异常调查：内部数据 → 网上资料 → 有证据的解释

通用入口说明见 [自然语言数据问答](DATA_QUESTION_AGENT.md)，本页只介绍异常调查场景。

2026-09-21；分支 `feature/crm-scoring-retrieval`；本地代码完成，不等于 AWS 已部署。

## 通用问答中的一个场景

问：“为什么这个月订单这么多？”

系统先明确月份/年份及业务市场，读取内部数据范围，按日分析订单，再围绕实际峰值日期查公开活动资料。最终回答展示内部证据、网页来源、候选解释和需要验证的地方。

例如：**在合成测试数据中**，普通日10单，6月17日80单，6月18日100单。工具会发现这两天是候选峰值；它没有写死“618”规则。随后可查询“中国 + 对应年份6月16—20日 + 电商活动”，让搜索结果告诉模型同期有什么活动。

模型最终可以说：“订单集中增长的日期与查到的活动日期一致，可能有关；还需确认我们的渠道和商品是否参加活动。”仅仅发现公共节日，不能写成“已经证明就是这个原因”。如果有内部活动编号、渠道和折扣数据，后续可以进一步提高归因可信度。

## 已实现

- `get_data_catalog`：先检查字段和数据日期范围。
- `analyze_order_spikes`：选择1—93天的区间，按指定 IANA 时区拆分每天订单。
- 返回每日记录数、订单金额、观察到的日订单中位数、前5个高峰日期、日期贡献比例、峰值 SKU 构成和样本记录ID。
- 候选峰值规则：至少7个有记录的日期，当日≥5单，且≥观察日中位数的3倍。这是可解释的筛选规则，不是校准过的异常概率；不控制星期效应，不证明因果。
- 没记录的日期只表示当前快照没有对应记录，不解释成企业当天真的没有业务。
- `search_public_events`：向 Tavily 发一次基本搜索请求，最多返回5条标题、URL、摘录、发布日期（可能为空）和检索时间。
- 日期、市场、话题由模型根据问题和内部工具结果选择。搜索请求没有自由文本字段，只能带公开国家、日期及枚举话题，避免把企业记录送出去。
- 已支持10个市场枚举及零售活动、公共假期、物流中断、天气影响4类话题；需要其他市场时可扩展 schema。
- 每个 Runtime run 最多2次网页搜索，无自动重试、不自动升级深度。MCP 每次调用各有自己的 run，因此此限制不代表跨会话总预算。
- 搜索配置缺失/失败/无结果时明确返回，不伪造“我查到了”。
- 浏览器展开 Evidence 可查看搜索调用与可点击的来源链接。所有工具调用仍走既有审计与持久化。

网页资料是外部背景，不会写入 Actual State，也不被标成企业内部事实。网页摘录是不可信数据，不能变成工具执行指令。工具只调用固定的搜索 API，不抓取模型给出的任意 URL。

## 配置入口：现在不需要密钥

默认关闭，不会调用搜索服务，也未消耗搜索或模型额度。

配置项已加入 `.env.example`：

```dotenv
BC_ENABLE_WEB_SEARCH=0
TAVILY_API_KEY=
```

之后有自己的 Tavily 搜索账号/密钥时，在**后端进程**的环境里设置：

```dotenv
BC_ENABLE_WEB_SEARCH=1
TAVILY_API_KEY=<在本机或服务器的私密配置中填写>
```

这不是 Bedrock/OpenClaw 模型密钥，不能通用。密钥不要放聊天、前端、截图或Git。按现有说明：API **不会自动读取 `.env`**；需由启动终端或服务管理器注入环境，设置后重启后端。若文件严格采用上面的 shell-compatible KEY=value 格式，可在可信的本地私密文件上使用 `set -a; source .env; set +a` 后启动；不要 source 不明来源文件。只在 `.env` 写入但不注入进程，不会生效。

真实自然语言分析还依赖原有 `BC_OPENCLAW_URL` / `BC_OPENCLAW_TOKEN` / `BC_OPENCLAW_AGENT_ID`。搜索服务可能消耗额度或收费，启用前查看自己账号的计划。本改动不注册账号、不购买服务、不调用付费接口。

接口实现依据：[Tavily 官方 Search API](https://docs.tavily.com/documentation/api-reference/endpoint/search)。固定 `search_depth=basic`、`auto_parameters=false`、`include_answer=false`，由我们的 LLM 根据带来源的摘录作解释。

## 示例调用

内部工具：

```json
{
  "start": "2026-06-01",
  "end": "2026-07-01",
  "timezone": "Asia/Shanghai",
  "filters": []
}
```

末日不包含。日界线跟时区走，避免北京时间6月18日凌晨被错分为6月17日。

发现峰值后，外部工具可使用：

```json
{
  "start_date": "2026-06-16",
  "end_date": "2026-06-20",
  "country": "China",
  "topic": "retail_events",
  "language": "zh"
}
```

外部日期是事件搜索上下文，不是强制网页发布日期过滤。模型要检查摘录中实际活动的年份和日期，不能拿旧活动、发布日期或别国事件直接解释订单。

界面问题示例：

> 分析中国市场2026年6月订单为什么集中增长。先看是否有该月数据，找出峰值日期和SKU，再搜索同期公开活动。引用内部数据与网页来源；没有证据时明确说不知道。

## 目前真实演示数据的限制

团队默认快照订单只有2026年8月末至9月上旬，没有六月数据，也没有渠道/活动编号/折扣字段。直接在当前数据问六月，应该返回缺少数据；不能把合成测试结果冒充当前企业事实。

`tests/fixtures/order_spike_618.json` 是**独立合成测试配置**，未导入业务库。它用来证明检测程序从数据发现6月17/18日，而不是硬编码节日；网页结果和多轮模型也使用测试替身，未做真实联网验收。

配置好真实模型与搜索后，还要用真实请求验收：查数据时没有预设618；使用正确年份与业务市场；网页来源可打开；区分“可能相关”和“已证实原因”；缺少六月记录时停止归因。不需要改主数据库才能运行这些测试。
